# Frontend TanStack Query migration plan

Date: November 3, 2026. Status: planned, except the separate SOF catalog cache change being implemented alongside this audit. No broad migration or production deployment is included in this plan.

Portlog already uses TanStack Query for most lists, forms, and operational workflows. Activities already use `useQuery`; the SOF failure comes from issuing a different search for each displayed saved label, exhausting the production search allowance. A shared catalog query addresses that incident. Other frontend paths still bypass TanStack and require a separate migration to meet the existing rule in `STACK.md`: all server reads through Query and all writes through mutations with explicit cache updates or invalidation.

## Boundaries that already comply

Transport helpers such as `apiRequest`, `apiUpload`, and `apiRequestBlob` remain necessary underneath query and mutation functions. Their existence is not a violation. Nested API calls inside a `mutationFn`, such as flag resolution during `SaveVesselModal` creation, already run within a mutation workflow. `EmailGroupPicker` resolves group members through `queryClient.fetchQuery`; its local resolving state does not make that read a bypass. `ServiceReport`, entity pickers, the attachment preview, and most existing domain hooks already use Query.

Authentication bootstrap and the client's token-refresh interceptor are a narrow transport exception: they establish or repair the credentials needed to run authenticated queries. Preserve refresh deduplication and logout isolation; do not route refresh through the same authenticated query path and introduce recursion or caching of tokens. Login and logout remain mutations and the current-user read remains a query. Document this exception beside the transport implementation.

Browser-only work does not require Query: file selection, editable form drafts, input debounce, CSV/Excel rendering from already retrieved data, object URL cleanup, navigation, and browser storage. A document download is not exempt simply because the user clicked a button; only the browser presentation after the server read stays outside Query.

## Migration sequence

1. **SOF request reduction.** Share one activity catalog cache across rows and filter locally. Displaying saved labels, adding rows, and sorting rows must not trigger per-label requests. Preserve saved selections if a catalog entry is deleted or a background refresh fails. Activity create/update/delete must invalidate the catalog along with relevant lists and timesheets. Reopening a fresh cached SOF should reuse the catalog; explicit invalidation must refresh it.
2. **Canonical query options.** Consolidate keys and options for detail, search, Datalastic, attachments, and document reads. Reuse existing options instead of creating parallel caches. Include all parameters that change the server response. Pass query cancellation signals through the transport. Choose freshness by domain; activity catalog freshness can be longer than live vessel data. Keep cache in memory and clear it on account changes/logout rather than persisting private data by default.
3. **Master data reads.** Convert the shared shell and FlashSearch, then the custom Ports screen. Preserve unsaved forms across background refreshes and explicit Cancel behavior. Use raw entity data in canonical detail caches and map into form values separately, avoiding incompatible cache shapes under an existing detail key.
4. **Domain mutations and files.** Convert direct writes and uploads to mutation hooks. Audit invalidation against every consumer, including compose data and picker searches. Replace local request booleans with mutation status where appropriate. Do not add automatic retries to creation, sending, or multi-step writes without an idempotency contract.
5. **Datalastic and document reads.** Convert selection/restoration reads and explicit lookup/export/download actions. An imperative `fetchQuery` still uses TanStack; an ordinary direct API call in a click handler does not. Bound fan-out even when queries use TanStack, since distinct keys are distinct requests.
6. **Enforce the boundary.** Add a lint/import or AST check that flags direct domain transport calls from UI effects and handlers unless they are inside a query/mutation function or named Query-client operation. Start with the confirmed inventory, then make the check required. Keep the transport/auth exception explicit. A text search alone cannot distinguish a legitimate nested mutation call from a bypass.

## Acceptance checks

- Mount a SOF with at least forty saved activities: one initial catalog request, no saved-label searches, no additional catalog request when sorting or adding rows, and reuse while fresh. Invalidation refreshes the catalog; a failed refresh retains saved selections and exposes a retry action.
- Navigate rapidly between master-data records while delaying responses: an older record cannot reset the new record's form. Cancel restores the selected record's persisted values; background refreshes do not silently discard edits.
- After each migrated write, verify all affected list/detail/picker/compose views update. Exercise a revision conflict and a partial file association or pier deletion failure; preserve the operator's recoverable work.
- Verify lookup/export actions share fresh data, separate different IDs and filters, honor cancellation, and avoid uncontrolled parallel requests.
- Verify server download errors and Blob cleanup, and verify logout clears domain caches and cannot reveal a previous user's cached data.
- Run focused behavioral tests for each migration, frontend typecheck and lint, then relevant workflow checks. Production rollout is a separate action after review; do not widen the SOF fix into this entire migration.

This is a static source audit and implementation plan. The production 429 evidence is recorded separately under the SOF investigation; this plan does not claim that the broader migration has been implemented or tested.
